# SDB 2.6.0 candidate data contracts

## Thermal and coupled models

Populate `ModelIR::foundation.thermal` with `admit_thermal_contract` from `sdb/input/thermal_contract.hpp`. Admission validates the coefficients, table shapes, material references and step IDs. `ModelCompiler` then resolves each region to a surface or element set. Physical values use the model's consistent unit system. Radiation constants and the absolute zero offset are explicit in that system. A surface flux measures heat per area and a body source measures heat per volume. Thermal contact stores the pressure, clearance and temperature axes in that order. An enthalpy table contains nondecreasing values, and a phase interval requires a nonnegative latent heat and strictly ordered endpoints. A coupled step records its scheme, both tolerances and the Taylor–Quinney fraction. Executing a thermal or coupled analysis belongs to the consuming solver.

Model schema 11 appends the versioned `THM1` section after all earlier fields. Schemas 1 through 10 keep their original field order, byte representation and identity rules for their index width. `ModelStore` round-trips the typed extension. Canonical model identity sorts named definitions but preserves axis, tensor component and step semantics. A changed contact property or thermal table changes semantic identity. `DC3D8` admits an eight-node, eight-integration-point storage descriptor.

## Section integration and plugin history

`integration_layout` accepts global element labels, continuum integration counts and a list of point counts per layer. Rows follow ascending element label, integration point, layer, section point. All four labels are one-based. Continuum rows use zeros for layer and section point. Beam fibers can be represented by one point per layer. Ragged offsets delimit each element. Use `integration_row` to look up a full address and `integration_layout_identity` to fingerprint the complete address sequence.

A `HistorySchemaDescriptor` declares a plugin ID/version and its named scalar or tensor slots. Each slot declares a field descriptor, ordered components, initialization and missing-value policy. `register_fields<FieldTypes...>` checks every typed slot before publishing the new registry. A successful registration replaces the registry's field objects. Acquire field views after registration and freezing. Persistent values must be finite. The masked policy represents a missing component with validity 0 and a canonical positive zero. `MultiBatchBundle` persists schema, initializers, addresses, values and masks using its existing atomic publication and restore checks.

## Distributed output and restore

Use a fresh directory for each generation and give every writer its rank, part count, common `PartitionEpoch` and `OwnedSourceMap`. Its label vectors use the writer's local row order. Labels are positive global uint64 values. Node and element labels occupy separate namespaces. For application models with scoped labels, the caller supplies a globally unique mapping. `OwnedSourceMap::from` accepts a local `SourceMap` with unique labels. An explicitly addressed field uses global labels in its full result addresses. An implicit entity field follows its local ownership vector.

Ranks independently call `PartitionedResultWriter::write` for committed sample frames and `PartitionedCheckpoint::write` for the final cursor. A single rank owns each filename. No inter-rank locking or collective is required. The coordinator calls `DistributedManifest::publish` after writers finish, supplying the authoritative global label sets and the expected epoch. The global constraint contract is optional. Each rank binds its own DOF identity and may receive a different local identity on restore. Global singleton rows (address zero) are replicated and compared byte-for-byte at every sample. A generation may publish results, checkpoints, or both. The coordinator checks per-rank membership, model/DOF/consumer identities, the entire step/increment/time axis, ownership, schema consistency, file extents and checksums before atomic publication. Existing shard filenames are immutable through the SDK writer. A failed publication leaves the previous manifest bytes intact.

The new formats have a fixed little-endian magic and 32-bit version 2, independent of SDK Index width. A version-1 candidate shard uses the saved epoch DOF identity as its rank-local identity during import. The manifest records rank, relative filename, file size, CRC-64/ECMA-182, index CRC64, global counts, ownership identity and axis identity. Each shard has a CRC32-framed header with its local source map, cursor, field schemas and row directory. Following it are entity-major component rows with canonical scalar bytes and optional per-component masks. Directory row CRC32 values support independent verification of selected rows. `DistributedManifest::open(path)` audits every index, row and whole-file digest. Readers check all index digests and extents and then verify each selected payload row.

`PartitionedResultReader` returns per-entity values in sample and full-address order. Sample intervals are half-open and time intervals are closed. Scalars retain their native type, including uint64 values above binary64's exact range. `PartitionedCheckpoint::restore` takes all target ownership sets, the destination rank, its committed registry and the expected epoch. It checks ownership completeness and every field schema, matches full row addresses and reads only the destination's value bytes. It stages one destination registry and publishes it after full value and mask validation. The return value reports the restored cursor, payload bytes, selected rows and source rows examined. Memory includes the global shard directories and a local staged registry. MPI communication and partition assignment are the caller's responsibility.

### Wave 3 audit revisions

The partition metadata budget defaults to 2 GiB per record. Supply the trailing byte budget on shard write, manifest publication or open, result-reader construction and checkpoint restore to fit the process memory envelope. Native decode also charges its container allocations against that budget. Resident indices, payloads and the destination state need additional memory. The v1 and v2 shard encodings retain their original layouts.

A checkpoint consumer can restore from the manifest and its checkpoint files alone. A result consumer requires the manifest and its result files. Full manifest publication and deep verification still check every advertised file. Restore compares the required replicated globals on all source ranks and skips the payload pass on disjoint nonzero ranks. Required fields restore from the checkpoint. Omitted and reconstructed fields receive their registered initializers, including when an older writer recorded extra rows. Result queries check finite values, mask bytes and the canonical positive zero of masked components.

## Verification entry points

Configure the standalone CMake project with `SDB_INDEX_BITS=32` or `64`. Run `ctest -R "^dbf1[01]_" --output-on-failure` for thermal and plugin history round trips, released SDK wire goldens, independent rank writers, result queries, repartitioned restore and fault injection. The freeze packet records the exact compilers, configurations, counts and cross-OS checks.
